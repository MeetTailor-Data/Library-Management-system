1. Executive Architecture Overview

The Smart Library Management System (SLMS) is a relational library information system designed specifically to adhere to academic faculty and university viva standards. The entire backend runs natively on PHP 8.x and MySQL under XAMPP.

Faculty Compliance Guarantee: The web application does NOT require Node.js, npm, or any external command-line server to function. All features—including student signup, authentication, book checkout/returns, inventory tracking, fine computation, and inquiry replies—are processed by native PHP scripts utilizing MySQL PDO prepared statements.

4. Step-by-Step Functional Workflows

This section outlines the exact sequence of events executed across the browser, JavaScript layer, PHP backend, and MySQL database for every critical system operation.

Workflow 1: Student Registration (Signup) Flow

  1. User Input: Student enters Full Name, Student ID (e.g. STU108), Email, Department, Academic Year, and Password on Pages/login.html?tab=signup.
  2. Client Validation: handleSignup(event) prevents default form submission and validates required fields and password matching.
  3. API Request: SLMS_STORE.addStudent() sends an HTTP POST request to ../backend/auth.php?action=signup with the JSON payload.
  4. PHP Controller: backend/auth.php invokes handle_signup(), parses JSON via get_request_data(), and checks MySQL for duplicate user_id or email.
  5. SQL Insertion: If unique, PHP runs: 
    INSERT INTO users (user_id, name, email, password, role, department, year, created_at)
VALUES ('STU108', 'Ankit Patel', 'ankit@example.com', 'test@2026', 'student', 'Computer Science', '1st Year', '2026-10-28');
  6. Session & Redirect: PHP returns { status: true, data: { ... } }. The browser saves the student in localStorage via setCurrentUser() and opens student-dashboard.html.

Workflow 2: Authentication & Role-Based Access Control (RBAC)

  1. Submission: User submits credentials (e.g., ADMIN01 and admin or STU106 and test@2026).
  2. PHP Verification: handle_login() queries MySQL: 
    SELECT * FROM users WHERE LOWER(user_id) = LOWER(?) OR LOWER(email) = LOWER(?) LIMIT 1
    Verifies password (plain string comparison or bcrypt password_verify()). Accepts both 'admin' and 'admin123' for the librarian role.
  3. Smart Routing:
    • If role === 'admin': Browser sets session and redirects to Pages/admin-dashboard.html.
    • If role === 'student': Browser sets session and redirects to Pages/student-dashboard.html.
  4. Route Guard: If a student attempts to navigate directly to admin-dashboard.html, auth-session.js detects user.role !== 'admin' and redirects them back to their student dashboard.

Workflow 3: Book Checkout / Issuing Engine

  1. Admin Request: Librarian opens "Issue Book" modal on admin-dashboard.html, selects a registered student (e.g. STU101) and an available book.
  2. Borrow Limit Verification: backend/circulation.php counts current active borrowings: 
    SELECT COUNT(*) FROM issued_books WHERE LOWER(user_id) = 'stu101' AND status != 'Returned'
    If count $\ge 3$, PHP returns error: "Borrow limit exceeded: Student already has 3 active borrowed books."
  3. ACID Concurrency Check: PHP begins transaction (beginTransaction()) and decrements stock atomically: 
    UPDATE books SET available_copies = available_copies - 1 WHERE id = ? AND available_copies > 0
    If stock was 0, transaction rolls back immediately.
  4. 14-Day Due Date Calculation: System computes default return deadline: 
    $dueDate = date('Y-m-d', strtotime('+14 days'));
  5. Commit: Transaction inserts record into issued_books with status 'Issued' and commits to MySQL. Both Admin and Student portals reflect updated quantities instantly.

Workflow 4: Book Return & Fine Calculation Engine

  1. Trigger: Librarian clicks "Mark as Returned" on circulation table.
  2. Fine Computation Algorithm (PHP): calculate_overdue_fine($due_date, $return_date) computes elapsed days: 
    if ($returnDate > $dueDate) {
    $overdueDays = $dueDate->diff($returnDate)->days;
    $fineAmount = $overdueDays * 5.00; // ₹5 per overdue day
}
  3. Stock Restoration: PHP increments available_copies back in books table: 
    UPDATE books SET available_copies = available_copies + 1 WHERE id = ?;
UPDATE issued_books SET status = 'Returned', return_date = '2026-10-28', fine = ? WHERE id = ?;
  4. Result: Book returns to catalog stock, student active borrow count decrements, and fines are permanently recorded.

Workflow 5: Contact Inquiry Submission & Admin Reply

  1. Public Message: Visitor submits inquiry on Pages/contect.html.
  2. Database Insert: backend/contact.php?action=submit inserts row into messages table with status = 'Unread'.
  3. Admin Panel View: Admin visits "Contact Messages" tab on admin-dashboard.html.
  4. Admin Reply Action:
    • Librarian clicks the "Reply" button and types response in prompt.
    • window.SLMS_STORE.replyMessage(id) sends HTTP POST with JSON {"id": 3} to backend/contact.php?action=reply.
    • PHP executes: 
      UPDATE messages SET status = 'Replied' WHERE id = ?
    • MySQL updates row status from 'Unread' to 'Replied'. The UI table badge updates to green Replied in real-time.

5. Faculty Presentation & Viva Cheat Sheet

Possible Faculty Question Ideal Technical Answer to Present
"Why did you use PHP instead of Node.js?" PHP is the industry-standard enterprise language for XAMPP / LAMP stack environments. It integrates natively with Apache and MySQL using PDO, requires zero runtime daemon management, and supports ACID database transactions seamlessly.
"How do you prevent SQL Injection?" All queries across auth.php, books.php, circulation.php, and contact.php utilize PDO Prepared Statements with Parameterized Placeholders (?). No user input is ever concatenated directly into SQL queries.
"What happens if two students try to borrow the last copy of a book at the same time?" The system executes an atomic transaction with UPDATE books SET available_copies = available_copies - 1 WHERE id = ? AND available_copies > 0. If the row count affected is 0, the second transaction is rolled back with an out-of-stock message, preventing negative stock concurrency bugs.
"How is the ₹5/day fine calculated?" When a book is issued, PHP calculates a 14-day due date (+14 days). During the return transaction or periodic view, PHP calculates the date interval difference between the due date and the return date. If overdue, it multiplies the elapsed days by ₹5.00.
"How does the frontend communicate with PHP?" The client uses standard asynchronous JavaScript fetch() requests wrapped inside slms-store.js. Responses are returned as structured JSON headers (Content-Type: application/json).
